# Building and testing

Commands to build, test, and pack Goop on Windows x64. One script runs the C++ build and the C# build.

## Prerequisites

| Requirement | Notes |
|---|---|
| **Windows, x64** | The only supported platform. `goop_native.dll` is 64-bit, and every managed project is pinned to x64 so it can load. |
| **Visual Studio 2022 or later** | With the **Desktop development with C++** workload. CMake detects the generator itself, so any recent version works. |
| **CMake 3.20+** | Either on `PATH`, or the **C++ CMake tools for Windows** component inside Visual Studio. `scripts/build.ps1` finds either. |
| **.NET SDK 10** | Builds all three target frameworks. The .NET 8 runtime must also be installed to run the `net8.0` tests. |
| **.NET Framework 4.8 Developer Pack** | Needed to *build* `net48`. The runtime alone lacks the reference assemblies. [Download](https://dotnet.microsoft.com/download/dotnet-framework/net48). |

## One command

```powershell
.\scripts\build.ps1                          # Debug
.\scripts\build.ps1 -Configuration Release
.\scripts\build.ps1 -SkipTests               # build and pack only
```

It runs seven steps and stops at the first failure, naming the step that failed:

1. CMake configure, into `build/`
2. CMake build → `build/bin/<Config>/goop_native.dll`
3. `ctest`: the C++ tests
4. `dotnet build dotnet\Goop.sln`: `net48`, `net8.0` and `net10.0`
5. `dotnet test dotnet\Goop.sln`
6. `dotnet pack` → `artifacts/packages/Goop.<version>.nupkg`
7. `Goop.PackageTests`: restores that `.nupkg` like an outside project and runs it

## The same steps by hand

```powershell
cmake --preset windows-x64
cmake --build --preset debug
ctest --preset debug

dotnet build dotnet\Goop.sln --configuration Debug
dotnet test  dotnet\Goop.sln --configuration Debug --settings dotnet\goop.runsettings

dotnet pack dotnet\src\Goop\Goop.csproj --configuration Debug
dotnet test dotnet\tests\Goop.PackageTests --configuration Debug --settings dotnet\goop.runsettings
```

`goop.runsettings` pins the test host to x64. Without it, VSTest may start a
32-bit host that cannot load the native DLL.

`Goop.PackageTests` is deliberately not in `Goop.sln`. It references Goop only
as a package, which does not exist until `dotnet pack` has run. See
[design.md](design.md#packaging) for how the package delivers the native DLL.

## Where the native DLL comes from

CMake writes `goop_native.dll` (and its `.pdb`) to `build/bin/<Config>/`. That
folder is outside the MSBuild graph, so the test and sample projects copy the
DLL next to their own output with an explicit target. If the native side hasn't
been built, `dotnet build` still succeeds, but warns (`GOOP0001`) that interop
calls will fail.

## Running the gallery

```powershell
dotnet run --project dotnet\samples\Goop.Gallery --framework net10.0
```

It writes STL files to `gallery/output/`, which is git-ignored. You can open them
in any 3D viewer.

## Formatting

```powershell
.\scripts\format.ps1          # rewrite the native sources with clang-format
.\scripts\format.ps1 -Check   # report drift, non-zero exit
```

## Debugging across the C# / C++ boundary

Stepping from C# into C++ needs the native debug engine loaded alongside the
managed one.

- **Gallery.** Already configured: its `launchSettings.json` sets
  `nativeDebugging: true`, so a breakpoint in `native/src/api.cpp` binds, and
  pressing F11 on a P/Invoke call steps into C++.
- **Tests.** VSTest owns its host process, so this is a Visual Studio setting:
  **Test > Options > Enable native code debugging**. It slows every run, so turn
  it off afterwards.
- Open `build/goop.slnx` (generated by CMake) for native work, and
  `dotnet/Goop.sln` for managed.

Both depend on `goop_native.pdb` sitting next to the DLL, which the copy target
takes care of.
